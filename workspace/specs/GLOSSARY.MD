# Glossary & Vocabulary

This file is the canonical vocabulary source for ServIQ documentation. Use these terms consistently across domain, technical, and product-facing docs.

## How to Use This Glossary

- Prefer the canonical term listed here when writing new documentation.
- If an older document uses a different term, keep the older term only when preserving historical context or compatibility.
- When renaming a term, update this glossary and the main index pages at the same time.

## Platform and Tenancy

- **ServIQ** — the multi-tenant service operations platform.
- **Platform** — the shared SaaS layer that serves all tenants.
- **Tenant** — a logically isolated customer instance on the platform.
- **Service Provider** — the business that operates inside a tenant and uses ServIQ to deliver services. Prefer this term when describing the business itself.
- **Platform Administrator** — the person who manages the shared ServIQ platform.
- **Tenant Administrator** — the person who manages one Service Provider's configuration, users, and operations.
- **Dispatcher** — the person who coordinates jobs, assignments, and operational exceptions for a Service Provider.
- **Service Agent** — the field worker who performs the service work.
- **Customer** — the person or organization that requests and receives the service.

## Customer Portal and Support

- **Customer Portal** — the customer-facing app or website used for signup, browsing, booking, tracking, and self-service.
- **Customer Support** — the tenant-facing support workflow for handling cases, complaints, follow-ups, escalations, and issue resolution.
- **Service Request** — the request a customer submits to receive service. Some older docs still say Customer Request, but Service Request is the preferred canonical term.
- **Service Job** — the scheduled operational work item created from a customer request.
- **Assignment** — the act of allocating a service job to a service agent.
- **Field Execution** — the on-site execution phase where the service agent completes the service job.
- **Workflow Template** — the ordered list of steps attached to a Service that defines how a job for that service is executed (for example, For Pick Up → Picked Up → In Transit → Delivered).
- **Workflow Instance** — the snapshot of a service's workflow template copied onto a Service Job; tracks each step as open, in-progress, or closed.

## Service Agent Portal

- **Service Agent Portal** — the service-agent-facing app or mobile portal used to accept assignments, view jobs, upload photos, upload proof of payment, capture customer confirmation, and complete the job. This is a presentation channel, not a standalone bounded context.

## Finance and Accounting

- **Tenant revenue** — income generated by a tenant's service operations.
- **Platform fee** — the amount retained by the platform from tenant activity.
- **Refund** — money returned to a customer after a charge or payment event.
- **Proof of Payment** — an uploaded receipt, screenshot, transfer confirmation, or similar document used to show that a payment was made.
- **Chargeback** — a payment reversal initiated through the payment processor or card network.
- **Payout** — money transferred to a tenant after fees and adjustments.
- **Fund Distribution** — the process of splitting a payment or net payable amount into explicit recipient buckets such as platform share, Service Provider share, Service Agent share, and other configured recipients.
- **Settlement** — the final status of a financial transaction after payment processing and reconciliation.
- **Reconciliation** — the process of matching platform records with payment processor records and internal financial data.
- **Remittance** — the confirmation that funds collected on the Service Provider's behalf (digital payments or physical cash) have been turned in and verified; records are marked `REMITTED` only on human confirmation, never on AI extraction alone.
- **Cash Turn-in** — the end-of-shift handover in which a Service Agent gives collected cash payments to a Dispatcher, verified against the expected collections list.
- **Remittance Batch** — a group of cash collections deposited together at a bank and collectively marked remitted against a single deposit slip's reference number and amount.

## Document Processing and AI

- **OCR** — Optical Character Recognition; the process of extracting text from images, scans, photos, or screenshots. Traditional OCR tools (e.g. Tesseract) extract text line-by-line and lose layout structure.
- **Vision LLM** — a large multimodal model that reads images directly, performing OCR while preserving layout and semantic structure; ServIQ's preferred approach for receipts, screenshots, and photographed documents. Also called LLM-powered OCR.
- **LLM** — Large Language Model; an AI model that interprets text and can classify, normalize, summarize, or generate structured output.
- **AI Agent** — the dedicated microservice (Python + FastAPI) that runs conversational agents backed by a shared LLM; responsible only for document reading/parsing, counting bills and coins, and sharing allowed information via tools. Business decisions stay in the domain microservices.
- **Agent Profile** — a named configuration (system prompt, tool registry, context binding) that scopes an AI Agent to one bounded context, such as the Customer or Dispatcher chatbot. Tools are never shared across profiles.
- **Agent Tool** — a callable capability exposed to one agent profile; every tool is an API call to the responsible microservice (or an external service) using the caller's JWT — never direct database access.

## Security and Access

- **Identity & Access (IAM)** — the dedicated bounded context and microservice that owns users, roles, and token issuance for the entire platform. The Tenant entity itself is owned by Platform Management; IAM consumes `tenant_id` purely as an authorization scope. Usernames are unique within their scope (tenant or platform), not globally.
- **JWT** — JSON Web Token; a signed token used to carry authenticated identity and claims for stateless API access.
- **JWT claim** — a named piece of data inside a JWT, such as a subject, tenant identifier, role list, permission list, or token metadata used for validation and authorization.

## Architecture Vocabulary

- **Bounded Context** — a domain boundary with its own model, responsibilities, and language.
- **Port** — an abstraction for an external capability such as messaging, persistence, or observability.
- **Adapter** — a concrete implementation of a port.
- **CQRS** — Command Query Responsibility Segregation; a pattern that separates command and query responsibilities.
- **Command Model** — the write side of CQRS; owns business rules and state changes, stored in PostgreSQL by default.
- **Read Model** — the query side of CQRS; a flat, denormalized view kept in sync with the command model by an event listener or subscriber. ServIQ uses one for the read-heavy Customer Portal channel (Express + MongoDB); internal services query their command models directly.
- **Event-Driven Architecture** — an architecture style that uses events to communicate changes between parts of the system.
- **Event Sourcing** — a persistence pattern where the event stream is the source of truth and current state is computed by replaying events; used by business-logic-heavy services such as Service Job Management, Billing, and Payouts.
- **Hexagonal Architecture** — an architecture style that keeps business logic isolated behind ports and adapters.
- **UUIDv7** — the time-ordered UUID variant used for domain entity identifiers such as `tenant_id` and `user_id`; globally unique and index-friendly.
- **SQID** — an encoded, non-predictable public identifier for transactional records (e.g. `Uk8xN2`); the service stores a sequential bigint internally and only ever exposes its SQID form, like YouTube video IDs.
- **Reference Number** — a human-readable display label for a transactional record (e.g. `JOB-1001`); unique per tenant and used on screens and in conversation, but never as the record identifier in API contracts or events.
- **Customer & Request Management** — the approved name of the Service Operations bounded context that owns Service Requests; the context name keeps "Customer" for the actor it serves while the requests inside it use the canonical "Service Request" term.
